# Sprint Retrospective: Sprint 1 (Proof of Concept)

**Focus:** Real-time Document Editing with CRDTs (Shared Spaces PoC)

| What went well | What went poorly | What ideas do you have | How should we take action |
| :--- | :--- | :--- | :--- |
| **Successful PoC Implementation:** We successfully integrated the `crdt` package and proved that real-time, decentralised document editing works across devices without a central server. | **Network Synchronization Debugging:** It was initially very difficult to debug P2P network synchronization issues over mDNS and TCP sockets when testing with multiple physical devices. | **Enhanced Network Logging:** Implement a dedicated, structured logging system specifically for network events, CRDT payload tracking, and connection drops. | **Action Item 1:** Integrate and standardize the use of `logger.dart` across all core network and sync services to trace CRDT vector clock states. |
| **Riverpod State Management:** Using Riverpod made it incredibly easy to reactively update the Flutter UI whenever a new CRDT delta was merged from a peer. | **Performance with Large Documents:** Handling complex or larger document states occasionally caused noticeable UI stuttering as the entire document string was rebuilt on every keystroke merge. | **Delta-Based UI Updates/Chunking:** Instead of replacing the entire text controller's value on every remote change, we should investigate using delta-based text controllers that only update the modified segments. | **Action Item 2:** Research and prototype using Flutter's `TextEditingDelta` or a custom document controller designed specifically for collaborative editing buffers. |
| **Offline-First Resilience:** The core concept held up perfectly; devices could go offline, edit the document, and successfully merge their changes without conflicts upon reconnecting. | **Testing Overhead:** Testing required spinning up multiple emulators or physical devices simultaneously, slowing down the iteration loop. | **Automated Local Peer Simulation:** Build a mock testing environment or test harness that can run multiple headless peer instances within the same test suite. | **Action Item 3:** Allocate time in the next sprint to set up a robust automated integration suite that simulates 3+ nodes communicating over localhost loopback. |
